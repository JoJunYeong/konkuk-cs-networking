# 관리자 화면 운영

## 접속과 로그인

GitHub Pages 공개 주소 뒤에 `/admin.html`을 붙여 접속한다. 화면에는 짧은 관리자 아이디를 입력하지만, 실제 로그인 확인은 Firebase Authentication이 맡는다.

- 비밀번호는 GitHub 저장소와 브라우저 코드에 저장하지 않는다.
- 로그인 상태는 현재 브라우저 탭 세션에만 유지한다.
- 관리자 화면은 검색엔진에 노출하지 않도록 `noindex, nofollow`를 적용했다.
- 화면 주소를 아는 것만으로는 자료를 저장할 수 없다. Firestore 보안 규칙이 로그인 계정을 다시 확인한다.

## 관리할 수 있는 내용

### 분기별 행사

- 새 분기 만들기와 목록 제외
- 첫 화면에 보여줄 회차 선택
- 신청 상태, 일정, 시간, 장소, 참가비, 정원 수정
- 한국 시간 기준 접수 마감 일시 설정과 자동 마감
- 회차별 외부 신청 URL 또는 자체 계좌이체 설정
- 자체 신청자 입금 일괄 대조와 확정
- 취소·환불 요청 처리와 환불 계좌 파기
- 큰 제목, 안내 문구, 모임 소개, 진행 순서 수정

로그인하면 현재 분기 또는 이후 분기 중 첫 화면 지정 회차를 우선 선택하고, 저장된 값을 바로 아래 편집기에 채운다. 다른 회차를 고르면 해당 회차의 저장값으로 입력칸이 즉시 바뀐다.

상단 행사 선택은 설정과 신청자 명단에 함께 적용된다. 전체 신청·입금 확인 대기·참여 확정·환불 요청 숫자를 누르면 해당 명단으로 이동한다. 이름, 입금자명, 휴대전화, 신청번호로 검색할 수 있다. 모바일에서는 신청자 한 명씩 카드로 표시한다.

진행 순서는 시간·내용·설명 입력칸으로 편집하고 위·아래 버튼으로 순서를 바꾼다. 설명은 비워도 된다. 소개 문구는 ‘소개 문구·세부 설정’에서 수정한다. 변경 사항은 저장 전까지 사이트에 반영되지 않으며, ‘변경 취소’로 되돌릴 수 있다. 다른 창에서 먼저 저장했다면 충돌을 알리고 덮어쓰지 않는다.

다음 분기 행사에서는 ‘이전 분기 내용’의 불러오기 버튼으로 가장 가까운 이전 회차의 저장된 설정을 가져올 수 있다. 버튼에 가져올 분기가 표시되며, 새 행사를 추가했을 때도 사용할 수 있다. 소개·공지, 행사 시간·장소·정원, 참가비·계좌·신청 방식, 진행 순서를 복사한다. 회차 이름·ID·첫 화면 지정, 행사 날짜, 접수 상태, 접수·환불 마감, 외부 신청 링크는 현재 행사 값을 유지한다. 이전 회차 원본은 바뀌지 않는다. 불러온 내용을 수정한 뒤 ‘변경 사항 저장’을 눌러야 사이트에 반영된다.

## 접수 마감 설정

공개 첫 화면에는 한국 날짜 기준 D-day, 초 단위 남은 시간, 정확한 마감 일시를 크게 표시한다. 마감일에는 `D-DAY`, 마감 시각 이후에는 `접수 마감`으로 자동 전환한다. 신청 영역에서도 D-day와 일시를 함께 확인할 수 있다.

## 공개 신청 인원

자체 계좌이체 회차의 ‘현재 신청’은 `payment_reported`와 `confirmed` 상태를 합산한다. 입금 확인 대기는 포함하고, `refund_completed`와 `canceled_unpaid`는 제외한다. 환불 요청만 접수된 단계에서는 신청 인원을 유지하며 관리자가 처리를 완료하면 감소한다. 외부 플랫폼 회차에는 이 숫자를 표시하지 않는다.

공개 `registrationStats/{eventId}`에는 `count`와 `updatedAt`만 저장한다. 새 신청은 신청 기록·비공개 `registrationCountUpdates/{eventId}` 증명·공개 인원을 하나의 배치로 저장한다. 서버 규칙은 새 신청 없는 증가, 재사용·중복 집계, 임의 숫자와 개인정보 추가를 거부한다. 관리자 취소·환불은 신청 상태와 인원을 같은 트랜잭션에서 변경한다. 공개 화면은 집계 문서를 구독해 바로 갱신하며, 조회 실패를 0명으로 표시하지 않는다.

기존 회차의 최초 집계는 관리자가 신청 상태를 확인해 초기화하며, 새로 만든 회차는 첫 저장 시 0명 집계를 함께 생성한다. 행사 설정 저장으로 기존 집계를 덮어쓰지 않는다. 관리자 화면의 ‘전체 신청’은 취소·환불 내역도 포함한 전체 기록이므로 공개 신청 인원과 다를 수 있다.

## 마감 일시 변경

‘행사 설정 → 접수 설정 → 접수 마감 일시’에 한국 날짜와 시간을 입력하고 저장한다. 해외 시간대로 설정된 컴퓨터에서도 한국 시간으로 저장한다. 정해진 시각부터 신규 신청이 차단되고 사이트에는 ‘접수 마감’으로 표시된다. 이미 열린 신청 화면에도 적용되며 Firestore 규칙이 서버 시간으로 다시 검사한다.

마감 일시를 비우면 자동 마감하지 않는다. 즉시 접수를 멈추려면 접수 상태를 ‘마감’으로 저장한다. 기한을 연장하려면 미래 일시로 바꾸고 상태가 ‘접수 중’인지 확인한다. 환불 요청 마감 안내는 별도 문구이며 접수 기간을 바꾸지 않는다. 기존 신청자의 입금 확인과 환불 처리는 접수 마감 후에도 가능하다. 외부 신청 페이지를 쓰면 해당 플랫폼의 접수 기간도 별도로 설정한다.

정확한 행사 주소는 Firestore의 공개 행사 설정에 적지 않는다. `공개 장소 범위`에는 `건대입구 인근` 정도만 적고, 실제 주소와 입장 방법은 입금 확정자에게 별도 공지한다. 자체 계좌이체를 선택한 회차의 은행·예금주·입금 계좌는 신청자에게 안내하기 위해 공개되는 정보다.

## 신청·결제·공지 운영

1. 회차의 신청 방식을 `계좌이체`로 고른다.
2. 입금용 은행, 예금주, 계좌번호, 재학생·졸업생 참가비와 환불 요청 마감 안내를 입력한다. 접수 마감 일시는 접수 설정에서 정한다.
3. 상태를 `접수 중`으로 저장한다. 행사 자료와 비공개 모집 게이트의 마감 일시가 한 번에 저장된다.
4. 신청자는 이름·휴대전화·입금자명을 입력하고 재학생 또는 졸업생을 선택한다. 입금 안내에는 선택한 구분의 금액이 표시된다. `계좌번호만 복사`로 숫자만 복사한 뒤 실제 송금하고 `입금완료 · 참여신청 마무리`를 눌러 접수를 완료한다.
5. `신청자·입금` 탭에서 직접 신청을 선택하거나, `은행 내역으로 일괄 확인`을 열어 `입금자명[TAB]금액` 두 열을 붙여 넣고 대조한다.
6. 선택한 이름과 금액을 확인한 뒤 `선택한 신청 입금 확인`을 누른다. 확인창에서 최종 확정한다.
7. 환불 요청이 오면 은행에서 실제 환불 송금을 마친 뒤 `환불 송금 완료`를 누른다. 완료 처리와 함께 환불 계좌 원문이 지워진다.

신청자가 누른 `입금완료 · 참여신청 마무리`는 `입금확인 대기` 상태만 만든다. 은행 거래내역을 직접 불러오는 연동은 없으며, 운영자가 실제 입금자명과 금액을 확인하기 전에는 참여 확정으로 바뀌지 않는다. 동명이인과 중복 입금은 자동 선택하지 않는다.

재학생·졸업생 참가비는 각각 1원부터 1,000,000원까지 정수로 설정한다. 기존에 참가비 하나만 저장한 회차는 두 입력칸에 기존 금액을 불러온다. 원하는 금액으로 바꾸고 저장하면 행사 안내와 신청 금액에 반영된다. 이전 분기 내용 불러오기에도 두 금액이 포함된다.

신청자 명단의 이름 아래에 참가 구분이 표시되며 `재학생` 또는 `졸업생`으로 검색할 수 있다. 이전 신청은 `구분 미수집`으로 표시한다. 참가비를 변경해도 기존 신청의 구분·신청 당시 금액은 바꾸지 않으며, 입금 대조와 환불은 기존 신청 기록을 기준으로 처리한다.

외부 신청 방식을 계속 쓰는 회차는 `https://` 공개 URL이 필요하다. 자체 방식은 은행·예금주·계좌번호·참가비가 모두 있어야 `접수 중`으로 저장할 수 있다.

회차 ID는 `2027-Q1` 형식을 사용한다. 첫 화면 회차를 여러 개 체크하면 현재 편집 중인 회차 하나만 남긴다.

### 지난 기록

- 날짜, 장소, 참여 인원, 공개용 설명 수정
- 주요 순서와 운영 메모 기록
- 새 기록 추가와 목록 제외

이름, 연락처, 이메일, 계좌번호, 참석자 사진은 넣지 않는다. 관리 화면은 긴 숫자열과 이메일 주소처럼 개인정보일 가능성이 큰 입력을 저장 전에 한 번 더 막는다.

## 저장 구조

공개 행사·기록은 다음 두 문서에 저장한다.

```text
siteData/events
siteData/history
```

공개 페이지는 같은 문서를 읽기 전용으로 불러온다. Firestore가 일시적으로 응답하지 않거나 문서가 아직 없으면 저장소의 `config/site.config.js`와 `data/history.json`을 보여준다.

자체 신청 자료는 별도 컬렉션에 저장한다.

```text
registrationGates/{eventId}   관리자 전용 모집 게이트
registrations/{randomId}      공개 생성, 관리자만 읽기·수정
refundRequests/{randomId}     신청번호와 휴대전화 일치 시 공개 생성, 관리자만 읽기·수정
```

공개 사용자는 신청·환불 요청을 만들 수만 있고 목록이나 개별 문서를 읽을 수 없다. 신청자는 자신의 신청번호를 보관해야 하며, 환불 요청은 해당 번호와 신청한 휴대전화가 모두 일치해야 접수된다.

## 신청 화면 검증

`node scripts/test-registration-submit.mjs`로 참가 구분별 신청, 신청자와 입금자명이 같은 경우, 구버전 숨김 `company` 필드의 자동완성 오탐, 필수 검증·마감·중복 제출 차단, 저장 실패 시 입력 보존을 확인한다. 신청 화면은 설정된 참가자 정보와 필수 동의만 사용하며, 숨김 회사명 값으로 정상 신청을 차단하지 않는다. 실제 입금 확인과 서버 보안 규칙은 그대로 유지한다.

## 보안 규칙 변경

로컬 규칙은 `firestore.rules`에 있다. Firebase CLI를 연결한 환경에서는 다음 명령으로 같은 규칙을 배포할 수 있다.

```bash
firebase emulators:exec --only firestore --project ku-cse-quarterly-admin \
  'node scripts/test-firestore-rules.mjs'
firebase deploy --only firestore:rules --project ku-cse-quarterly-admin
```

규칙 테스트는 모집 게이트가 닫혔을 때 신청 차단, 유효한 신청 허용, 공개 읽기 차단, 금액 위조 차단, 신청번호·휴대전화가 일치하는 환불 요청만 허용하는지를 확인한다.

게이트의 `registrationDeadline`은 Firestore timestamp 또는 명시적 null이어야 한다. 값이 없거나 형식이 틀리면 신청을 차단한다. 기존 게이트에 이 필드를 추가한 뒤 새 규칙을 배포해야 한다. 마감 전·후, 명시적 무기한, 잘못된 마감 값, 마감 이후 기존 신청 처리도 테스트한다. 시간 변환 검사는 `node scripts/test-registration-time.mjs`로 실행한다.

행사와 모집 게이트의 `paymentAmounts`는 `student`·`graduate` 금액을 담는다. 새 신청은 `participantType`과 해당 금액을 저장하고 규칙이 일치 여부를 확인한다. 구분별 금액을 아직 저장하지 않은 기존 게이트는 단일 `amount` 방식도 허용한다. 새 규칙을 먼저 배포한 뒤 화면을 배포하며, 이미 구분별 금액을 저장한 게이트를 구버전 관리자가 단일 금액으로 덮어쓰는 요청은 차단한다. 오류가 나면 관리자와 신청 페이지를 새로고침한다. 참가비 계산 검사는 `node scripts/test-registration-fees.mjs`로 실행한다.

로컬 관리자 검증은 Authentication과 Firestore 에뮬레이터를 함께 띄우고 `http://127.0.0.1:PORT/admin.html?firestoreEmulator=127.0.0.1:FIRESTORE_PORT&authEmulator=127.0.0.1:AUTH_PORT`로 접속한다. 두 에뮬레이터는 `demo-ku-networking` 프로젝트를 사용하고 관리자 UID의 테스트 계정을 별도로 만든다. 외부 도메인에서는 에뮬레이터 옵션을 사용하지 않는다.

관리자 계정을 바꾸면 다음 세 곳을 함께 확인한다.

1. Firebase Authentication의 사용자 계정
2. `config/firebase.config.js`의 화면용 아이디와 로그인 별칭
3. `firestore.rules`의 허용 계정 UID

클라이언트의 Firebase 웹 설정은 공개 식별자이며 비밀키가 아니다. 실제 쓰기 권한은 Authentication과 Firestore 규칙이 결정한다. 서비스 계정 키, Firebase Admin SDK 키, 비밀번호는 저장소에 넣지 않는다.

## Notion과 함께 쓸 때

Notion 동기화는 `data/history.json` 예비본만 갱신한다. 관리자 화면에서 Firestore 기록을 만든 뒤에는 Firestore가 공개 페이지의 기준이므로 Notion 변경이 자동으로 덮어쓰지 않는다. 평소 운영은 관리자 화면 하나로 하고, Notion은 과거 원문 보관이나 정적 예비본 갱신에만 쓰는 것을 권장한다.
